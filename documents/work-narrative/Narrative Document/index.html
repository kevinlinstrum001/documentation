Work Narrative · First Cycle

Learning to See the Work

A reconstructed history of the Meadows Housekeeping / Klinswork project cycle — from small operational tools to a much larger lesson about systems, identity, evidence, documentation, and how to preserve the story of work while it is still happening.

This project did not begin with an ontology, a formal architecture, or even a settled definition of the system being built. It began close to the floor: supplies that moved, tasks that had to be completed, rooms that needed names, products that needed information, assignments that changed, and small recurring problems that seemed as though software might help.

The first tools were practical experiments. As they were built, tested, corrected, and sometimes replaced, they exposed a deeper problem: to support housekeeping work accurately, the project first had to understand what the work actually was. A location was not a dispenser. A task was not the operational function behind the task. An application was not the department. A record of current state was not the same thing as the history that produced it.

Over roughly a month, the work gradually shifted from making useful interfaces to modeling an operational environment — and then shifted again, toward preserving enough evidence and narrative that a future reader could reconstruct not only what had been built, but why the project had changed direction along the way.

A rule for reading this history

Capability does not imply adoption. A tool may have been designed, built, tested, demonstrated, personally used, piloted, or made available without becoming the department-wide way the operation was conducted. This narrative distinguishes the operational function from the software that attempted to support it.

Chronology

One problem kept revealing another

The sequence matters. Later concepts should not be projected backward onto earlier work as though they had been obvious from the beginning.

16 July

The first boundary problem

Four separate Apps Script HTML views — Intake, Work Queue, Recommendations, and Completed Work — failed when navigation occurred inside the embedded environment. The initial temptation was to suspect the action logic. Testing cleared the backend.

The solution was not to rewrite the queue. It was to stop navigating between separate embedded pages and keep the user inside one persistent Dashboard.html. The system worked end to end once the interface boundary was changed.

Lesson: a visible failure can occur at the interface boundary even when the underlying data and action logic are correct. Diagnose the layer before replacing the system.

19 July

Inventory starts behaving like a history

The inventory tool matured beyond a simple quantity sheet. It supported Received, Used Up, Removed, Moved, and Count Corrected transactions. Accepted requests changed current quantities and also created permanent events; invalid requests could be diagnosed without producing partial changes or false history.

Definitions, current state, submitted requests, accepted events, locations, and SDS information became distinct concerns. Product View and an SDS Directory made the information reusable beyond a single form.

Emerging distinction: what is true now and what happened over time are different kinds of information. Current state and append-only event history began separating naturally because the work demanded it.

21 July

Inventory 3.0: replace rather than endlessly patch

Instead of continuing to patch the earlier implementation, Inventory 3.0 began as a fresh architecture with clearer responsibilities: configuration, data access, inventory services, and validation. Cart quantities, adjustment reasons, and event history became more deliberate.

A Tool Center brought Inventory 3.0, Tasker, and Email Composer together. What had looked like several isolated utilities started to resemble a personal work-software environment.

Method change: when accumulated patches obscure the intended model, a clean implementation can be safer than preserving every earlier assumption.

23 July

A deployment address becomes an architectural rule

Product pages, browser views, SDS material, and research links increased the usefulness of the inventory environment — but another routing problem appeared through a temporary script.googleusercontent.com/userCodeAppPanel address.

The correction was to have the server provide the deployed application URL using ScriptApp.getService().getUrl(), then expose it to the page as window.APP_URL.

Rule established: one stable deployment address should act as both the front door and the authoritative routing source. A temporary frame location is not application identity.

25 July

Work Queue 2.0: define the work before the interface

The old Tasker was replaced rather than patched. This time the purpose, boundaries, workflow, and data ownership were defined first. Tasks moved through Pending → In Progress → Completed, could be reopened, and every meaningful action generated activity history.

The project was working with eight units and 163 active locations. Tasks represented current state while Task_Activity preserved the append-only record of what happened. Backend lifecycle testing came before interface polish.

Another repetition: the current object and the history of changes to that object should not be collapsed into one record.

26 July

The dispenser is not the room

A modeling error became visible: locations and physical operational objects had been treated as though they were the same kind of thing. The system could identify where work occurred, but not precisely which physical object had been affected.

Inventory_Holders were introduced and attached to locations, along with holder events. The model could now distinguish a restroom from the toilet-paper dispenser inside it. At this stage, 267 restroom holders were represented across 89 restroom locations in seven units.

Generalized lesson: place and object identity must remain separate. “Where?” and “what physical thing?” are different questions even when the answers are operationally close together.

30 July

Scheduling reveals identity, assignment, and override

The Housekeeping Calendar separated Employees, Assignments, and Locations. Employees received stable EMP-### identities. An assignment connected a person, date, location, shift, and status rather than baking those facts into the person record.

Normal schedules, temporary exceptions, and the final resolved schedule were treated separately. Cancellation became an override rather than deletion.

Emerging grammar: identity, state, occurrence, assignment, and history were becoming reusable concepts — not because a formal ontology had been planned, but because ordinary housekeeping situations kept requiring them.

1 August

The documentation problem becomes visible

By August, the project had accumulated applications, HTML pages, sidecars, screenshots, conversations, repositories, catalogs, and project knowledge. There was plenty of documentation, but much of the logic connecting it still lived implicitly in conversation and memory.

The work turned toward an authoritative narrative source, durable project records, project relationships, boundaries, sidecars, project deltas, audience-specific views, and a repeatable publication pipeline.

Most importantly, the project identified what ordinary accomplishment lists were losing: the prompting situation, initial understanding, chosen approach, misleading paths, evidence that changed the model, turning points, decisions, and lessons.

Documentation changed roles: it was no longer merely evidence that software existed. It was becoming a mechanism for reconstructing the reasoning that created the system.

8–9 August

“Work Queue” is not the system

A semantic correction reorganized the project. Work Queue was an application implementing part of a durable operational undertaking: Task Assignment and Tracking. The same distinction applied elsewhere. The application name, file path, or deployment address could change while the underlying operational purpose persisted.

The Resource Registry introduced stable RES-### identity and resource activity history. A bootstrap record, RES-000, helped a fresh context find the authorities it needed instead of depending on remembered conversation.

Identity rule: resource identity is not resource location. More broadly, implementation is not the thing being implemented.

15 August

The model corrects itself again

A more explicit identity architecture separated project, system, resource, hierarchy, and operational function. “Child Project” was recognized as a relationship rather than a different type of project. Operational Function remained distinct from the software system serving it.

The working invariant became unusually important:

identity != name != location != hierarchy != status != implementation

The project also deliberately refused to assign premature Project IDs while an allocator conflict remained unresolved. Uncertainty was preserved rather than hidden.

Historical caution: this vocabulary describes a mature understanding reached in August. It should not be rewritten into the July story as though it had existed from the start.

16 August

Can another context reconstruct the work?

Formal Work Unit machinery was used prospectively, including WORK-0001 — Task Assignment and Tracking — Initial Project Definition. Then the documentation system was subjected to a more revealing test: a fresh ChatGPT context was asked to reconstruct the durable records after the original work context had closed.

The Two-Window Test exposed routing weaknesses, stale or ambiguous resources, global-versus-local context problems, and places where technical state and documentation did not reconcile cleanly. Those failures drove another redesign.

By the end of the day, the Work Update Summary had become the canonical Markdown master from which sidecar JSON, HTML, project deltas, and other downstream products could be derived.

Success criterion changed: a record was not good merely because the author understood it today. It needed to make the work reconstructable later at the level of meaning, not merely output.

The central movement of the first cycle: software problems repeatedly turned into modeling problems, and modeling problems eventually turned into documentation problems. Each layer forced the project to describe the real work more carefully.

Mature interpretation

The tools were not the operation

The later project summary makes an important correction: housekeeping existed before, during, and outside the software. People, rooms, supplies, paper records, verbal reports, assignments, observations, and physical work were the operational environment. The applications represented or supported pieces of that reality.

Inventory Management

Operational function: obtaining, moving, staging, issuing, restocking, consuming, and reconciling supplies.

Software support: Inventory 3.0, product views, SDS material, cart inventory, holder events, and related records.

Task Assignment & Tracking

Operational function: receiving work, assigning it, locating it, changing status, completing it, reopening it, and preserving what happened.

Software support: Tasker, later Work Queue 2.0 / 2.1, task activity history, locations, and holder-linked work.

Scheduling

Operational function: resolving who is expected to work, where, when, under what normal schedule or exception.

Software support: Housekeeping Calendar, stable employee identities, assignments, exceptions, and overrides.

A physical process the software was learning to describe

Supply Room→Housekeeping Closet→Employee Cart→Restocking Work→Holder / Dispenser→Operational Consumption

The mature model could distinguish the location in which something existed, the physical asset or holder itself, the inventory event affecting supply state, and the holder event describing what happened to the operational object.

The project became more accurate each time it stopped asking “How should the app represent this?” and first asked “What is the real thing we are trying to describe?”
Retrospective synthesis

The documentation turn

The most valuable artifact was almost disposable

For much of the project, rich end-of-session summaries were created in conversation, then used to generate structured sidecars and HTML updates. The downstream artifacts were saved. The richest human-readable source summary often was not.

Earlier workflow

  1. Work session / conversation
  2. Rich narrative summary generated in chat
  3. Sidecar JSON derived from the summary
  4. HTML Work Update and other outputs produced
  5. The source narrative could disappear with chat history
→

Mature workflow

  1. Work session / actual evidence
  2. Master summary.md saved durably
  3. Sidecar JSON derived from the master
  4. HTML, project delta, email, image brief, and other views derived downstream
  5. The causal story remains recoverable even if presentations change
We were generating the most valuable intellectual artifact and then using it as disposable intermediate state.
Lesson recovered from the first cycle

Why the sidecars matter

Narrative became analyzable data

The Work Update sidecars did more than label files. They preserved a recurring reasoning structure: the problem that prompted the work, the initial model, the intended outcome, the approach, the progression, failed or misleading approaches, turning points, key decisions, generalized methods, and results.

Checkpoint record

Work Unit Activities

What materially happened? Sparse in count but dense in notes. One activity could preserve an entire implementation or validation stage rather than recording every click as a separate event.

Human narrative

Work Update Summary

How did the work unfold? Chronological and causal prose preserving context, uncertainty, wrong turns, evidence, decisions, and what the work taught.

Structured interpretation

Work Update Sidecar

What was the reasoning structure? A machine-readable analytical record of prompting situation, initial understanding, progression, failures, turning points, decisions, lessons, and result.

Surviving evidence

Four records now tell the story together

No single artifact contains the entire history. The first cycle becomes legible only when the different evidence types are read together and allowed to keep their different jobs.

Historical method

This page is a retrospective synthesis based on surviving project records. Where later documents provide clearer vocabulary, that vocabulary is used to interpret the mature system — but not to pretend the project possessed that understanding earlier than the record shows. Tool capability is described separately from operational adoption.

What survived the first cycle

Some applications may remain useful. Some may be replaced. Some may never matter operationally beyond the situations in which they were built and tested. That does not make the work disappear. The durable product of the first cycle is larger than any one interface: a growing method for observing a real environment, distinguishing the things inside it, testing representations against reality, recording changes without erasing history, and preserving enough narrative that future work can begin from evidence rather than memory.

The project also produced its own test of that method. This document was created later, after the original sessions had passed, by reading the Work Updates, sidecars, activity history, Projects Summary, and technical manual together. The documentation architecture was designed to make old work reconstructable. The fact that the story can now be recovered — including its wrong turns and changes of mind — is evidence that the architecture eventually began doing exactly that.

The first cycle therefore ends in a different place than it began. It started by trying to make housekeeping tools. It ended by learning how to preserve the development of understanding itself.
