# Documentation Workflow Upgrade — 2026-08-09

**Target workflow:** `documentation-workflow.json`  
**Working status:** Upgrade notes only; workflow JSON not yet revised  
**Date:** 2026-08-09

## Purpose

This document preserves the architectural changes identified on 2026-08-09 for the next revision of the **Klinswork Project Change and Documentation Workflow**.

The existing workflow already has the correct general shape:

1. establish current project and integration context;
2. preserve a pre-work intention;
3. open a bounded work-session conversation;
4. inspect and modify the actual implementation;
5. test and collect evidence;
6. interpret what changed;
7. reconcile durable project and integration state;
8. generate, publish, index, and verify documentation artifacts.

The upgrade described here does **not** replace that model. It makes the context-acquisition and documentation-reconciliation stages more concrete by incorporating the new **Klinswork Tools Resource Registry**, canonical project/resource documentation, repository-level README files, and a root `repository-manifest.json`.

The central architectural principle is:

> **Bottom-up work establishes truth; top-down structure makes that truth navigable.**

---

## 1. New Context-Loading Architecture

The Resource Registry is becoming the principal top-level entry point for Klinswork work sessions.

A future ChatGPT work session will normally begin with the user providing the **Klinswork Tools Resource Registry**. The assistant should then navigate progressively rather than attempting to load the entire environment.

Expected context path:

```text
Klinswork Tools Resource Registry
        ↓
README FIRST / Registry operating context
        ↓
relevant project and resource rows
        ↓
PROJECT ID + METADATA REFERENCE
        ↓
canonical project / resource documentation
        ↓
repository README when repository work is involved
        ↓
repository-manifest.json for physical file discovery
        ↓
specific implementation artifacts only as needed
```

The workflow should explicitly recognize this as the normal context-establishment process.

### Context-loading rule

The assistant should acquire only enough context to perform the current task reliably.

It should:

- begin with the Registry;
- identify the relevant project or projects;
- follow canonical context references;
- use repository or subsystem manifests for location discovery;
- inspect individual implementation artifacts only when needed;
- stop retrieving when the current task is sufficiently understood.

It should **not** recursively open every link or file exposed by the Registry, project documentation, README files, or manifests.

---

## 2. Resource Registry Role

The workflow currently refers generically to a project registry and project files. The upgraded workflow should explicitly recognize the **Klinswork Tools Resource Registry** as a separate authority and routing layer.

The Resource Registry answers questions such as:

- What resources exist?
- Where are they?
- Which project owns or uses them?
- What are they for?
- Where is their authoritative context?
- What changed recently?

Relevant registry fields include:

- stable Resource ID;
- Name;
- Project ID;
- Link;
- Description;
- Metadata Reference;
- Last Update.

The Registry should be treated primarily as an **inventory and routing layer**, not as the location of all project knowledge.

### Registry activity history

Meaningful Registry mutations must continue to create Activity records.

A work session that discovers missing, obsolete, or incorrect registry information should treat that discovery as a documentation-maintenance outcome.

---

## 3. Canonical Project and Resource Documentation

The workflow should recognize a layered documentation structure.

Conceptually:

```text
Resource Registry
        ↓
canonical project / resource README
        ↓
deeper documentation
        ↓
implementation artifacts and historical evidence
```

Canonical project and resource documents carry semantic meaning that should not be duplicated unnecessarily into Registry rows or generated manifests.

These documents should explain, where applicable:

- purpose;
- scope and boundaries;
- architecture;
- represented operational system;
- implementations;
- data sources;
- dependencies;
- relationships;
- authority;
- lifecycle/status;
- navigation to deeper artifacts;
- unresolved questions;
- historical context.

The workflow should prefer canonical documentation over assumptions inferred from filenames, directory placement, or application behavior.

---

## 4. Repository README Role

When a work session is routed into the Documentation repository or another repository, the repository-level `README.md` becomes the next orientation layer.

For the Documentation repository, the README should explicitly explain that it is normally being read in the context of a **Klinswork Tools Registry-guided work session**.

Its role is to explain:

- what the repository is;
- what it is not;
- major functional areas;
- authority distinctions;
- generated vs. source artifacts;
- how to use repository manifests;
- URL-construction rules;
- how to descend into subsystem documentation;
- how to leave durable documentation after new architectural discoveries.

The repository README describes the repository, not all of Klinswork.

System-level relationships remain the responsibility of the Resource Registry and project-level documentation.

---

## 5. Root Repository Manifest

Add a root repository inventory:

```text
repository-manifest.json
```

and a generator such as:

```text
build_repository_manifest.py
```

### Primary function

`repository-manifest.json` should answer:

> **What physically exists in this repository, and where is it?**

It should recursively expose repository-relative file and directory paths plus useful factual metadata.

Possible fields include:

- `path`
- `name`
- `parent`
- `type`
- `extension`
- `size`
- `modifiedTimestamp`
- `archived`
- generation timestamp

The manifest should be **descriptive rather than interpretive**.

Semantic interpretation belongs primarily to:

- the Resource Registry;
- canonical project documentation;
- canonical resource documentation;
- repository and subsystem README files;
- sidecars and other structured records.

### URL construction

The repository README should define known URL bases so paths in `repository-manifest.json` can be used to construct likely source and GitHub Pages URLs.

Example conceptual relationship:

```text
repository-relative path
        +
GitHub source base
        =
source URL

repository-relative path
        +
GitHub Pages base
        =
hosted static URL when applicable
```

The manifest enables discovery and URL construction without forcing a work session to crawl the repository.

### Freshness

The manifest represents the repository at its recorded generation time.

It should be treated as a discovery index, not proof that no later repository changes occurred.

Avoid claiming that the manifest represents the commit containing itself unless a safe mechanism is designed. A `baseCommit` field may be possible later, but a generation timestamp is sufficient initially.

## 6. Bounded Work-Session Context Package

The existing workflow correctly requires a fresh work-session conversation to receive only materially relevant context.

The upgraded workflow should make the context package more **routing-oriented**.

Instead of copying a large body of documentation into the conversation, the package may contain:

- `workSessionId`
- `documentationRunId`
- primary Project ID
- approved work-session intention
- Resource Registry URL
- relevant Resource IDs
- canonical project-document URL
- relevant resource metadata references
- repository README location
- repository-manifest location
- directly relevant source artifacts
- relevant integration records
- known tests or operational examples

The execution conversation can then navigate further only when required.

The context package should provide enough information for the new conversation to answer:

> Where am I, what am I changing, what should I trust, and where do I look next?

---

## 7. Top-Down Navigation / Bottom-Up Reconciliation

The upgraded workflow should explicitly describe the two directions of documentation movement.

### During context acquisition

Navigation is **top-down**:

```text
Registry
    ↓
Project
    ↓
Resource
    ↓
README / manifest
    ↓
specific implementation artifact
```

### During work and documentation

Knowledge is reconciled **bottom-up**:

```text
actual implementation / evidence
        ↑
resource-level understanding
        ↑
project-level documentation
        ↑
Resource Registry
```

This is especially important because Klinswork project documentation will be developed by systematically organizing the actual underlying resources and records.

High-level project documents should therefore be syntheses of lower-level evidence, not speculative descriptions imposed before the implementation is understood.

---

## 8. Work-Session Discovery Types

The current workflow already records newly discovered projects, integrations, data propagation, risks, tests, failures, and decisions.

The upgraded workflow should also treat the following as first-class discoveries:

- newly discovered resources;
- unregistered resources;
- new repository file locations;
- moved or renamed artifacts;
- stale or missing Registry links;
- missing Project IDs;
- missing Metadata References;
- missing canonical READMEs;
- incorrect project placement;
- newly identified source/generated relationships;
- newly identified generator/consumer relationships;
- obsolete canonical URLs;
- superseded implementations;
- documentation conflicts;
- discrepancies between canonical documentation and actual implementation;
- repository-manifest gaps or stale entries.

These discoveries may be documentation outputs even when they are not part of the original implementation goal.

---

## 9. Reconciliation Stage Upgrade

The existing project/integration reconciliation stage should be expanded.

After the evidence-supported change interpretation has been approved, determine whether the work changed:

- the actual implementation;
- resource identity or location;
- resource-level meaning;
- project-level meaning;
- project state;
- roadmap state;
- integrations;
- canonical URLs;
- Registry relationships;
- documentation routing.

Where applicable, reconciliation should proceed upward:

1. update the authoritative implementation/source artifact;
2. update or create resource-level documentation;
3. update project documentation;
4. update project/integration structured records;
5. update Registry fields and relationships;
6. append Registry Activity records for meaningful Registry changes;
7. preserve unresolved questions rather than guessing.

Not every session requires every layer.

Applicability should be determined from actual changes.

---

## 10. Generated Artifacts and Manifest Maintenance

The workflow already requires generated catalogs, metadata, indexes, and manifests to be regenerated and validated against their sources.

The new root repository manifest should join this maintenance model.

If repository contents are materially:

- added;
- removed;
- renamed;
- moved;

then regenerate:

```text
repository-manifest.json
```

before final repository closure.

This should occur alongside any other affected specialized generators, for example:

- JSON Viewer manifest;
- image manifest;
- catalogs;
- catalog metadata;
- documentation indexes.

### Generated-file rule

Before editing a generated artifact, determine whether its generator is the proper change target.

Generated outputs should not become accidental sources of truth when an authoritative generator exists.

---

## 11. Publication and Commit Sequence

For repository-affecting work, the later workflow should conceptually become:

```text
finalize authoritative source changes
        ↓
update relevant documentation
        ↓
regenerate specialized catalogs / manifests
        ↓
regenerate repository-manifest.json
        ↓
validate generated outputs
        ↓
commit and push
        ↓
verify canonical URLs
        ↓
update Registry if required
        ↓
record Registry Activity
        ↓
final verification
```

The exact placement of Registry updates relative to publication may depend on when canonical URLs become available.

---

## 12. Final Verification Upgrade

The final workflow verification should include, when applicable:

- resource-level documentation updated;
- project-level documentation reconciled;
- project/integration authorities updated;
- Resource Registry updated;
- Registry Activity recorded;
- generated catalogs regenerated;
- image manifest regenerated;
- JSON Viewer manifest regenerated;
- `repository-manifest.json` regenerated;
- canonical source URLs verified;
- GitHub Pages URLs verified where applicable;
- unresolved documentation gaps recorded;
- stale routing information removed or classified.

These checks should be conditional, not mandatory busywork for every session.

## 13. Artifact Authority Additions

The workflow's authority model should eventually add explicit roles for:

### Klinswork Tools Resource Registry

Authoritative for registered resource identity and routing information, including:

- Resource ID;
- registered resource name;
- current registered link;
- Project ID association;
- Metadata Reference;
- Registry change history.

### Registry README / README FIRST

Authoritative for:

- Registry purpose;
- field semantics;
- maintenance rules;
- context-loading procedure;
- controlled-write expectations;
- interpretation of missing fields.

### Canonical project/resource README

Authoritative for:

- semantic meaning;
- purpose;
- scope;
- architecture;
- intended relationships;
- navigation to deeper artifacts.

### Repository README

Authoritative for:

- repository role;
- repository-level navigation;
- source/generated distinctions;
- repository-specific operating rules.

### `repository-manifest.json`

Authoritative only for:

- generated physical repository inventory as of its generation time.

It should **not** be treated as the semantic authority for project membership or resource meaning.

---

## 14. Workflow Purpose Expansion

The workflow currently exists to control project changes and preserve documentation about what occurred.

Its purpose should now explicitly include preserving the **future navigability of Klinswork**.

A revised conceptual purpose is:

> Perform bounded work, preserve the pre-work intention, collect evidence, reconcile what was learned from the implementation upward into durable resource and project context, publish appropriate documentation artifacts, and leave enough authoritative routing information that a future human or AI work session can recover the necessary context efficiently from the top down.

The documentation process therefore does more than record completed work.

It continuously improves the system's ability to explain itself.

---

## 15. Core Design Principle to Preserve

The upgraded workflow should preserve this reciprocal architecture:

```text
BUILDING THE KNOWLEDGE

actual files / apps / data
        ↑
resource documentation
        ↑
project documentation
        ↑
Klinswork Tools Resource Registry


USING THE KNOWLEDGE

Klinswork Tools Resource Registry
        ↓
project documentation
        ↓
resource documentation / manifests
        ↓
actual files / apps / data
```

The goal is not to load all Klinswork information into every work session.

The goal is to maintain enough structure, authority, relationships, and routing information that each session can determine **what it needs to read next**.
