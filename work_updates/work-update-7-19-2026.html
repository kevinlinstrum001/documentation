Inventory Processing and Reusable Web Views

This update covers major progress on the Klinswork Inventory system, including the transaction processor, product and SDS views, routing, and navigation. The system can now record inventory as it is received, used, removed, moved, or corrected, while stopping invalid requests before they create inaccurate records. It also brings product details, current quantities by location, and safety documents together in reusable web views, with a shared navigation system that resolved the instability caused by embedded Apps Script pages.

For housekeeping, this means staff can keep track of what they have, where it is, and how it is being used without relying on scattered notes or memory. Supervisors gain a much clearer view of inventory activity, shortages, corrections, and product information, increasing visibility and accountability across the team. Future versions will expand this structure to every employee, supply closet, and storeroom, creating a much richer picture of how supplies move across the entire operation. Imagine the data: usage patterns, recurring shortages, overstocked areas, transfer needs, and a reliable history that supports better planning and faster decisions.

Overview

Work completed across Milestones 6 and 7 moved the project from a collection of spreadsheet records and experimental pages into a functioning inventory application with validated transactions, permanent event history, live product information, current SDS access, and reusable browser views.

Milestone 6 established the processing layer. Accepted inventory requests now update current quantities and create permanent operational events. Invalid requests remain available for diagnosis but cannot change inventory or create false event records.

Milestone 7 then connected that data to a routed web application. The current interface includes Home, Inventory, Product Directory, reusable Product Detail, and SDS Directory views. The Product View combines product identity, an image, manufacturer information, inventory by location, and the current SDS record.

The project now separates product definitions, current inventory, submitted requests, accepted inventory events, locations, and SDS records while presenting them through a consistent web interface.

Embedded Navigation Problem and Solution

The route map worked, but page-to-page navigation became unstable when Apps Script pages were used inside an embedded environment.

Problem

Relative links such as ?view=inventory depended on the browser resolving the correct frame and base URL. Links could work when opened directly yet fail, disappear, or replace the wrong frame when embedded.

→

Solution

The server now provides one shared appUrl to every template. Navigation links use the complete Apps Script web-app URL and send every request back through doGet(e) and the route map.

Why the problem occurred

Host page
└── embedded Apps Script web app
    └── sandboxed Apps Script HTML view

In this structure, target="_top", target="_parent", and relative paths can refer to different frame levels depending on how the application was opened. Routing and navigation therefore had to be treated as separate systems.

Stable navigation flow

User clicks complete appUrl link
→ Apps Script deployment receives request
→ doGet(e) reads the view parameter
→ route map selects the HTML template
→ destination view renders

The shared URL was added to Home, Inventory, Product Directory, Product View, and SDS Directory navigation. Product links use the same base URL with a stable product ID, such as ?view=product&id=CHEM-001.

Verification

Testing covered both successful operating paths and deliberate failure cases.

  • Received inventory increased the correct destination quantity.
  • Used Up and Removed actions reduced the correct source quantity.
  • Moved inventory preserved the total while changing locations.
  • Count Corrected replaced the recorded amount with the verified count.
  • Unknown destinations produced no partial source subtraction.
  • Over-limit removals and moves produced no negative inventory.
  • Rejected requests remained visible for diagnosis but created no operational event.
  • The same Product View displayed different products when only the ID changed.
  • Inventory-by-location displayed the correct matching records.
  • Current SDS records and document links loaded from live sheet data.
  • Shared navigation worked across all existing views.
  • The existing Inventory View continued to function after routing changes.
Result Milestone 6 is complete, and Milestone 7 is approximately 70–75% complete. The application now has a safe transaction processor and a stable routed interface, not merely a set of independent spreadsheet forms and prototype pages.
