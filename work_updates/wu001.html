Work Queue and Recommendation Queue Implementation Plan

A staged development and testing plan for moving from the current intake log viewer to a complete operational workflow with sorting, queue views, status changes, notes, completion records, and completion email notifications.

Contents

Target workflow 1. Sheet structure 2. Intake buttons 3. Queue writers 4. Persistent sorting state 5. Work Queue viewer 6. Recommendations viewer 7. Status changes 8. JSON notes 9. Completed filtering 10. Completion email 11. Completed view 12. Archiving Final system test Implementation order

Target workflow

Supervisor submits form → Source record is created → Source record is normalized → Intake viewer displays the record → User sorts it into Work Queue or Recommendations Queue → A working record is created using the source ID → Queue viewer combines the source record with the working record → Status and notes are updated on the working record → Completed work leaves the active queue → Completion email is sent → Record remains available in completed history and may later be archived

The system should be built in small, testable stages. Each stage must produce one visible and reliable result before the next function is added.

1Define the sheet structure

The current spreadsheet already contains:

Form Responses
Normalized

Add two new tabs:

Work Queue
Recommendations Queue

Work Queue columns

Column Purpose
Source ID Links the working record to the normalized source record.
Status Pending, In Progress, Completed, and later Archived.
Sorted At Timestamp showing when the item entered the queue.
Started At Timestamp showing when work began.
Completed At Timestamp showing when work finished.
Updated At Most recent change to the working record.
Notes JSON A JSON array containing notes and history entries.
Completion Email Sent Prevents duplicate completion emails.

Recommendations Queue columns

Column Purpose
Source ID Links the recommendation to the original source record.
Status Unreviewed, Reviewed, Converted, or Archived.
Sorted At Timestamp showing when it entered the queue.
Updated At Most recent change.
Notes JSON JSON history for comments or review notes.

Stage 1 tests

  • Create one manual test row in each queue.
  • Confirm the headers are spelled consistently.
  • Confirm Source ID values remain text.
  • Confirm timestamps display correctly.
  • Confirm [] remains valid text in Notes JSON.
  • Confirm Apps Script can find each tab by name.
  • Delete the manual test rows after verification.

2Add sorting controls to the intake viewer

Add two buttons to every unsorted source-record card:

[Send to Work Queue]
[Send to Recommendations Queue]

Each button must pass the card's unique source ID:

sendToWorkQueue(sourceId);
sendToRecommendationsQueue(sourceId);

At first, the buttons can act as placeholders and only display the selected source ID in the browser console or on the card.

Stage 2 tests

  • Every card displays both buttons.
  • Each button returns the correct Source ID.
  • Clicking one card does not affect another card.
  • The buttons work on both laptop and mobile views.
  • Expected ID characters such as numbers and hyphens pass correctly.
  • No sheet changes occur yet.

3Create queue-writing functions

Apps Script functions will accept a Source ID and append a new working record to the correct queue sheet.

New Work Queue record

{
  "sourceId": "REQ-0042",
  "status": "Pending",
  "sortedAt": "current timestamp",
  "startedAt": "",
  "completedAt": "",
  "updatedAt": "current timestamp",
  "notes": [],
  "completionEmailSent": false
}

New Recommendations Queue record

{
  "sourceId": "REQ-0043",
  "status": "Unreviewed",
  "sortedAt": "current timestamp",
  "updatedAt": "current timestamp",
  "notes": []
}

Before appending, the function must check both queue tabs. The same Source ID should not be allowed to enter both queues accidentally.

Stage 3 tests

  1. Send one source record to Work Queue.
  2. Send one source record to Recommendations Queue.
  3. Confirm the correct row appears in each sheet.
  4. Confirm the source record itself is unchanged.
  5. Click the same button twice and confirm no duplicate is created.
  6. Try placing the same Source ID in the other queue and confirm rejection.
  7. Refresh the viewer and confirm queue records remain.

A successful function can return:

{
  "success": true,
  "queue": "work",
  "sourceId": "REQ-0042"
}

A duplicate attempt can return:

{
  "success": false,
  "reason": "already-sorted"
}

4Make sorting state persistent in the intake viewer

The intake viewer must load:

  • normalized source records;
  • Work Queue Source IDs;
  • Recommendations Queue Source IDs.

It then combines those lists before rendering.

An unsorted card shows:

[Send to Work Queue]
[Send to Recommendations Queue]

A sorted card shows:

Sorted to Work Queue

or:

Sorted to Recommendations

Stage 4 tests

  • Sorted cards remain marked after refresh.
  • Sorting buttons do not reappear on handled records.
  • Unsorted cards still show both buttons.
  • Queue labels are correct.
  • Duplicate sorting is blocked even from two open browser tabs.

5Build the Work Queue viewer

The Work Queue viewer begins with working records from the Work Queue sheet. For each Source ID, it retrieves the original normalized source record and combines the two. 

Mop Sagebrush

Submitted: July 12, 8:15 AM
Sorted: July 12, 8:20 AM
Status: Pending

Notes:
No notes yet.

[Start Work] [Add Note] [Complete]

The active Work Queue should normally show only:

Pending
In Progress

Stage 5 tests

  • Each Work Queue row produces exactly one card.
  • The correct original request text is retrieved.
  • Source IDs match the correct source records.
  • No recommendation appears in the Work Queue.
  • A missing source record produces a warning card, not a page failure.
  • An empty queue displays “No active tasks.”
  • The viewer remains correct after refresh.

6Build the Recommendations Queue viewer

Each recommendation card should combine:

  • the original recommendation text;
  • the current recommendation status;
  • notes;
  • the sorting timestamp.

The first version may use:

Unreviewed
Reviewed
Archived

Later statuses can include:

Converted to Work
Declined
Accepted

Stage 6 tests

  • Only recommendations appear in this viewer.
  • Each card displays the correct original content.
  • Recommendations never trigger work-completion email behavior.
  • Notes can be added without changing the source record.
  • Empty and malformed records are handled safely.

7Add task status changes

Initial task statuses:

Pending
In Progress
Completed

Allowed transitions:

Pending → In Progress
Pending → Completed
In Progress → Completed

Initially disallowed:

Completed → In Progress
Completed → Pending

When Start Work is clicked:

  • set Status to In Progress;
  • set Started At only if it is blank;
  • update Updated At.

When Complete is clicked:

  • set Status to Completed;
  • set Completed At only if it is blank;
  • update Updated At.
If a task is completed directly from Pending, the first version can set Started At = Completed At. This avoids missing duration data for immediate tasks.

Stage 7 tests

  • Pending changes to In Progress.
  • In Progress changes to Completed.
  • Pending can change directly to Completed.
  • Clicking Start twice does not replace Started At.
  • Clicking Complete twice does not replace Completed At.
  • Invalid backward transitions are rejected.
  • Original source data remains unchanged.

8Add task notes using JSON

Initial value:

[]

After one note:

[
  {
    "createdAt": "2026-07-12T09:30:00",
    "text": "Waiting for the floor machine."
  }
]

After another:

[
  {
    "createdAt": "2026-07-12T09:30:00",
    "text": "Waiting for the floor machine."
  },
  {
    "createdAt": "2026-07-12T10:05:00",
    "text": "Floor machine is available."
  }
]

The Add Note function should:

  1. read the existing Notes JSON cell;
  2. parse it;
  3. verify that it is an array;
  4. append the new note;
  5. convert the array back to JSON text;
  6. write it back to the sheet;
  7. update Updated At.

Stage 8 tests

  • Add the first note to an empty array.
  • Add several notes and preserve earlier entries.
  • Test commas, quotation marks, apostrophes, and line breaks.
  • Reject blank notes.
  • Handle malformed JSON without losing existing data.
  • Refresh and confirm notes remain in chronological order.

9Remove completed work from the active queue

Completed records should not be deleted from the Work Queue sheet. The active viewer should simply filter them out. 

Active viewer:
Status = Pending or In Progress

Completed viewer:
Status = Completed

Stage 9 tests

  • A completed task disappears from the active Work Queue.
  • The same task appears in the Completed view.
  • The source record still exists.
  • The working record still exists.
  • Timestamps and notes remain intact.
  • Refreshing does not return it to the active queue.

10Send the completion email

The completion email should be sent only after the working record is successfully completed.

Verify current status → Write Completed status → Write Completed At → Save working record → Send email → Mark Completion Email Sent = true

The recipient should come from the original or normalized source record.

The completion email may include:

  • the original request;
  • the Source ID;
  • the completion timestamp;
  • the final note, when appropriate;
  • a viewer link, when available.
The script must check Completion Email Sent = false before sending. If email delivery fails, the task may remain Completed while the email flag remains false so the email can be retried safely.

Stage 10 tests

  • Completing a task sends exactly one email.
  • Refreshing sends no second email.
  • Pressing Complete again sends no second email.
  • The correct recipient receives the email.
  • The message contains the correct Source ID and request.
  • A missing or invalid email address does not break the queue.
  • A failed send leaves the email flag false.
  • A retry function can send the email later.
  • Recommendations never trigger completion emails.

11Add a completed-work view

The Completed view should show:

  • the original request;
  • Started At;
  • Completed At;
  • duration, when available;
  • notes;
  • whether the completion email was sent.

Duration can be calculated later:

Duration = Completed At − Started At

Stage 11 tests

  • Every completed task appears once.
  • Active tasks do not appear.
  • Missing timestamps do not break duration display.
  • Notes remain readable.
  • Email-delivery state is visible.
  • Records remain after refresh.

12Add archiving later

Archiving should be added only after the active lifecycle is reliable. The simplest first version is: 

Status = Archived
Archived At = timestamp

The original source record remains unchanged. Archived records load only when the Archive view is requested.

Stage 12 tests

  • Archived tasks disappear from the Completed view.
  • Archived tasks appear in the Archive view.
  • They still retrieve their original source record.
  • Notes and timestamps remain intact.
  • Archiving does not delete anything.

Final end-to-end system test

Use a test request such as:

Mop Sagebrush hallway

  2. Confirm the raw response is written.
  3. Confirm the normalized source record is created.
  4. Confirm the intake viewer displays the card.
  5. Sort it into Work Queue.
  6. Confirm one working record is created.
  7. Confirm the intake card shows that it has been sorted.
  8. Open the Work Queue viewer.
  9. Confirm the original request and Pending status appear.
  10. Start the task.
  11. Confirm Started At is written.
  12. Add two notes.
  13. Confirm both notes remain.
  14. Complete the task.
  15. Confirm Completed At is written.
  16. Confirm the item leaves the active queue.
  17. Confirm it appears in Completed.
  18. Confirm exactly one completion email is sent.
  19. Refresh every viewer.
  20. Confirm all state remains correct.
  21. Confirm the original source record was never changed.

Recommended implementation order

  1. Create the queue tabs.
  2. Add intake-viewer buttons.
  3. Write sorting functions.
  4. Make sorting state persistent in the intake viewer.
  5. Build the Work Queue viewer.
  6. Build the Recommendations viewer.
  7. Add status changes.
  8. Add JSON notes.
  9. Add Completed filtering and view.
  10. Add completion email.
  11. Add Archive.
  12. Add validation and backups.
Every stage must be proven with visible test records before the next stage is added.

This prevents the queue, status, notes, email, and archive systems from all being debugged at the same time.
