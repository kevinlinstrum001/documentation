1

Application scope and architecture

We began by deciding that the existing Tasker app should be replaced rather than incrementally repaired. Before writing code, we defined Work Queue 2.0's purpose, boundaries, workflow, data ownership, and relationship to the wider Klinswork tool system.

Core workflow: Pending → In Progress → Completed, with the ability to reopen completed work and preserve every action in a permanent activity history.
  • Create tasks directly inside the application.
  • Remove the old Google Form intake.
  • Eliminate the Recommendations feature.
  • Separate active work from completed work.
  • Keep Work Queue compatible with other Klinswork tools.
  • Build it as a separate project so the older Tasker deployment could remain online during development.
2

Shared location architecture

A centralized location directory was designed before the task system itself. This prevents Inventory 3.0, Work Queue, and future scheduling tools from maintaining separate copies of the same location data.

Shared directory

Klinswork_Locations became the common reference source for units, rooms, offices, restrooms, common areas, and other work locations.

Completed coverage

  • 8 units
  • 163 active Work Queue locations
  • Application-specific enablement
  • Reusable parent-and-child relationships

This was also one of the first major uses of direct spreadsheet generation and editing, substantially reducing repetitive setup work.

3

Operational data structure

A separate spreadsheet was created for Work Queue 2.0 operational data.

Tasks

Stores each task's current state, including ID, status, priority, category, location, description, assignee, timestamps, completion note, and archived state.

Task_Activity

Stores the full chronological history of task creation, starts, notes, completions, reopenings, and later changes.

Settings

Stores app version, default priority, completion-note requirements, notification settings, and location cache duration.

Task_Templates

Provides the foundation for reusable task choices that reduce typing during task creation.

Work Queue does not overwrite task history. Every action is appended as a new activity record, creating a true audit trail.

Modular Apps Script backend

The backend was divided into focused files rather than written as one large script.

FileResponsibility
Config.gsSpreadsheet IDs, sheet names, app name, version, and configuration.
Code.gsSetup, diagnostics, and backend test functions.
WebApp.gsWeb app entry point and startup data.
Validation.gsConfiguration, schema, input, status, and transition validation.
Utilities.gsIDs, dates, formatting, normalization, sorting, and user attribution.
LocationService.gsShared location retrieval and unit/location resolution.
TaskService.gsComplete task lifecycle, spreadsheet persistence, and activity logging.

Backend-first testing

One of the most valuable process improvements of the day was testing the backend directly through Apps Script → Run → test function before launching the interface.

Created → Started → Note added → Completed → Reopened → Completed again

Tests covered spreadsheet setup, schema validation, location retrieval, task creation, notes, status transitions, activity history, and startup data.

Startup summary

  • App: Work Queue 2.0
  • 8 units
  • 163 locations
  • Default priority: Normal

Why this mattered

It isolated backend problems before introducing browser JavaScript, interface rendering, deployment versions, filters, and modals.

Early interface issue: Scripts.html initially contained CSS rather than JavaScript. The page looked correct but remained on “Loading Work Queue.” The file was corrected, the deployment was updated, and the application came to life.

Created and completed a real task

A new task was created entirely through the interface using a selected unit, selected location, free-text category, free-text assignee, description, initial note, and normal priority.

The interface correctly:

  • Changed the button label while saving.
  • Saved the task to the spreadsheet.
  • Displayed a green success notification.
  • Refreshed the task collections.
  • Opened the new task automatically.
  • Displayed its task ID and metadata.
  • Recorded creation and the initial note as separate activities.
  • Moved the task into Completed Work after completion.
9

Real error handling

During one completion attempt, the browser experienced an HTTP 0 connection failure. This became a useful real-world test of the app's recovery behavior.

The app did correctly

  • Displayed the failure visibly.
  • Did not falsely report success.
  • Preserved the completion note.
  • Allowed the user to retry.

After retry

  • The task completed successfully.
  • The task moved into Completed Work.
  • The task history remained intact.

Development lessons

Test the backend first

Data structure → backend services → compact test functions → startup response → interface → real workflow testing

Use direct spreadsheet assistance

Direct Google Sheets editing can now accelerate table creation, reference data, formatting, validation, frozen headers, settings, and column sizing.

Visible feedback is part of functionality. A user should never have to wonder whether an action registered or whether the application is still working.
