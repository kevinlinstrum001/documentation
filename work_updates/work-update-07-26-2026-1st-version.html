1

A fundamental redesign, not a routine update

The day began with a strategic decision: stop modifying the working application directly and create a fully separate Work Queue 2.1 Beta. That decision protected the stable release while giving the beta enough freedom to become something substantially more capable.

Templates define what should happen. Locations identify where it happens. Holders identify what physical object is affected. Tasks record requested work. Holder events record what happened to the object.

This distinction resolved a central data-modeling problem. Rooms, restrooms, hallways, closets, and units remain locations. Soap dispensers, toilet-paper dispensers, towel dispensers, shelves, cabinets, carts, and other physical containers are represented as inventory holders attached to those locations.

Location → Holder → Product → Holder Event → Work Queue Task

6

Implemented the inventory-holder architecture

The new holder model represents physical operational objects separately from locations. This gives Work Queue a precise answer to both where the work occurs and what object is affected.

Inventory_Holders

Stores holder identity, type, location, position, service area, product assignment, capacity, tracking method, current state, condition, active status, and notes.

Inventory_Holder_Events

Stores append-only history including event type, previous and new state, condition, product, quantity, related task, timestamp, recorder, and notes.

7

Expanded the Tasks schema from 18 to 23 columns

Five new fields completed the task-template-holder-event chain:

New task field Purpose
Template ID Records which task template defined the work.
Related Holder ID Identifies the physical holder affected by the task.
Completion Event Type Defines the holder event that completion should record.
Completion State Defines the holder state expected after completion.
Related Holder Event ID Links the completed task to its append-only holder event.
Important cleanup discovery: the old setup code still knew only the original 18 columns. It was corrected to use the same required-header functions as services and validation, eliminating a major source of future schema drift.
8

Made task creation server-controlled

Manual task

May be created without a template, holder, completion event, or holder-event linkage.

Holder-free template task

Saves its Template ID while remaining free of holder and holder-event fields.

Holder-required task

Requires a valid, active, compatible holder at the selected location.

Server validation now confirms

  • The template exists, is active, and applies to the selected location.
  • The holder exists, is active, and belongs to the selected location.
  • The holder type and product category match template requirements.
  • Completion Event Type and Completion State come from server-side template data.
  • Invalid combinations are rejected rather than saved incompletely.

10

Created an append-only holder event service

InventoryHolderEventService.gs now owns holder-event creation, retrieval, sorting, task linkage, duplicate prevention, holder-state synchronization, and script-lock protection.

Event ID format: IHE-XXXXXXXXXXXX Task completion → find existing event for task → create only when necessary → update holder state → save event ID to task → preserve append-only history

Duplicate prevention

Repeated automatic event requests for the same task resolve to the existing event rather than creating another row.

Shared responsibilities

Task completion calls the event service, while holder-state updates remain delegated to InventoryHolderService.gs.

11

Connected task completion to holder history

Validate Task → Validate Holder → Resolve Event → Update Holder → Complete Task

Holder-linked completion creates or reuses exactly one event, updates the holder to the template-defined completion state, saves the event ID to the task, and writes normal task activity. Holder-free and manual tasks complete without creating holder events.

History-preservation rule

  • Reopening preserves Related Holder ID and Related Holder Event ID.
  • The original holder event is never deleted or modified.
  • Holder state is not automatically reversed.
  • Re-completion reuses the original event.
  • A second automatic holder event is not created.
One automatic holder event per task, preserved through reopening and re-completion.
