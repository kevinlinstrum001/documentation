We created a responsive Google Apps Script calendar application for viewing the Meadows housekeeping schedule. The app began as a basic schedule viewer and developed into a polished desktop-and-mobile calendar with day and month views, live schedule data, assignment details, navigation controls, cancellation controls, and a consistent visual system.

3. Designed the schedule-resolution architecture

We decided that the app should eventually distinguish between:

the normal schedule
temporary exceptions
the final resolved schedule

The planned resolution order is:

1. Read the employee’s regular weekly schedule
2. Read any employee-specific schedule events
3. Apply overrides for the selected date
4. Return the final resolved assignment

The main schedule-event types discussed were:

TIME_OFF
CALL_OFF
CANCEL_ASSIGNMENT
REASSIGNMENT
SHIFT_CHANGE
EXTRA_SHIFT

This allows the original assignment to remain available for history while the calendar displays the corrected result.

6. Built the Apps Script web entry point

Code.gs

We created doGet() to serve the application:

function doGet() {
  return HtmlService
    .createTemplateFromFile("Index")
    .evaluate()
    .setTitle(CONFIG.APP_NAME)
    .addMetaTag(
      "viewport",
      "width=device-width, initial-scale=1"
    );
}

We also created an include helper:

function include(filename) {
  return HtmlService
    .createHtmlOutputFromFile(filename)
    .getContent();
}

The server exposes calendar data through a function such as:

function getCalendarData(startDate, endDate) {
  return ScheduleService.getCalendarData(
    startDate,
    endDate
  );
}

9. Built the schedule service

ScheduleService.gs

The schedule service:

  1. Reads active employees.
  2. Reads enabled locations.
  3. Reads assignments within the requested range.
  4. Resolves employee IDs to employee names.
  5. Resolves location IDs to display names.
  6. Groups assignments by work date.
  7. Returns a browser-friendly calendar object.

A returned assignment contains values such as:

{
  assignmentId: "ASN-...",
  employeeId: "EMP-014",
  employeeName: "Amor",
  locationId: "JUNIPER-N",
  locationName: "Juniper North",
  shiftStart: "07:00",
  shiftEnd: "15:30",
  status: "SCHEDULED"
}

The data is grouped by date so the browser can quickly retrieve:

CalendarState.data.days["2026-08-01"]

12. Fixed an initialization failure

At one point the browser reported:

Uncaught TypeError:
Cannot read properties of null
(reading 'addEventListener')

The cause was that initialize() attempted to attach listeners to elements that were missing or not yet available.

We rewrote initialization so it:

  1. Finds all required elements.
  2. Builds a list of missing elements.
  3. Logs a clear error if anything is absent.
  4. Stops initialization instead of crashing.
  5. Treats optional controls such as Refresh safely.

We also discovered that a pasted file labeled as App.html actually contained CSS from Styles.html. That was caused by copy-and-paste lag, so we began checking the actual contents rather than relying only on the pasted filename.

13. Created client-side calendar state

ClientData.html

We introduced a central state object for the browser:

const CalendarState = {
  view: "month",
  visibleDate: new Date(),
  selectedDate: new Date(),
  data: null
};

The client-data layer handles:

loading visible calendar data
refreshing calendar data
normalizing server responses
storing assignments
returning assignments for a date

The app loads a buffered range rather than only the exact visible day.

For month view, it can load enough data for:

the previous month
the visible month
the following month

For day view, it can load a range around the selected date.

That reduces unnecessary server calls during normal navigation.

The desktop application was changed to use approximately:

width: min(calc(100% - 48px), 1280px);

This gave the calendar more room on large screens while preserving side margins.

The month grid and details panel were balanced so neither felt cramped.

27. Softened the month-grid lines

The original cell borders were dark and visually dominant.

We replaced individual dark borders with a one-pixel grid-gap method:

.month-grid {
  gap: 1px;
  padding: 1px;
  background: var(--border);
}

.month-day {
  border: 0;
}

The neutral background shows through the one-pixel gaps, producing cleaner grid separators.

35. Reduced stylesheet redundancy

Over several design rounds, Styles.html accumulated:

the original styles
desktop-refinement overrides
polished-desktop overrides
day-color overrides
additional mobile overrides

This caused the file to become difficult to predict because later rules silently overrode earlier ones.

The stylesheet reached roughly:

1,100 lines

The first cleanup attempt still left the original rules plus another theme block appended to the bottom.

We recognized that this was not a true overhaul.

We then rebuilt Styles.html as a genuine replacement with:

one root color system
one base layout
one controls section
one month-view section
one desktop section
one day-view section
one modal section
one mobile breakpoint
one small-phone breakpoint

The cleaned replacement was approximately:

797 lines

The important improvement was not just the line count. It removed competing definitions so future style changes can be made directly rather than through additional override blocks.
