Next step

What routing means

Routing means a human looks at a submission card and decides where that submission belongs next. The original log entry is not moved or changed. Instead, the routing action creates a new derived record in a working buffer.

Route to Task Route to Meeting Notes Route to Suggestions Needs More Info Archive

These buttons are not intelligence yet. They are simple human decisions captured through the browser interface.

Core rule

Never change the history log

Submission_Log should remain append-only. It answers one question: What was submitted?

The working buffers answer different questions:

Task_BufferWhat needs action?
Meeting_NotesWhat should be discussed later?
SuggestionsWhat ideas or improvements were submitted?
Needs_InfoWhat cannot be acted on yet?
ArchiveWhat was reviewed and requires no further action?

Do not move records out of Submission_Log. A route creates a copy or derivative that points back to the original submission ID.

How the route works

The routing path

The browser card is the visible interface. Apps Script remains the controller. Google Sheets remains the storage layer.

Important detail

The button should not send the entire JSON object from the browser. It should send only:

{
  "submission_id": "6d0ec3a5-...",
  "route": "task"
}

Then Apps Script looks up the real JSON inside Submission_Log. That keeps the log as the source of truth.

Data model

Source record vs routed record

The source record and the task record are related, but they are not the same thing.

Record type Where it lives Purpose Can it change?
Submission record Submission_Log Permanent history of what was submitted No; append-only
Task record Task_Buffer Action item derived from a submission Yes; status, priority, notes, completion details
Meeting note Meeting_Notes Item saved for discussion Yes; can be reviewed, grouped, or closed
Suggestion Suggestions Idea or recommendation for later consideration Yes; can be accepted, rejected, or parked
Example

What a derived task might look like

When a submission is routed to the task buffer, the new record should carry its own task fields while preserving a link to the source submission.

{
  "task_id": "task-2026-0711-001",
  "source_submission_id": "6d0ec3a5-...",
  "created_at": "2026-07-11 12:45",
  "route": "task",
  "status": "New",
  "priority": "Unassigned",
  "task_title": "Review submitted cleanup issue",
  "location": "Unknown until reviewed",
  "description": "Derived from original submission card",
  "source_json": {
    "submission_id": "6d0ec3a5-...",
    "submitted_at": "2026-07-11 12:42",
    "non_empty_answers": []
  }
}

The task is a working object. The source JSON is the evidence underneath it.

Build sequence

Safe order of work

  1. Keep the existing card viewer working. Do not disturb the capture/log/view pipeline.
  2. Add visible buttons to each card. At first, the buttons can do nothing or only show a test message.
  3. Add a routing function in Apps Script. The browser calls it with a submission ID and destination.
  4. Create destination sheets. Start with Task_Buffer, then add other buffers later.
  5. Append a derived record. Do not edit the original log row.
  6. Show feedback on the card. Example: “Routed to Task_Buffer.”
  7. Add a separate Tasks page later. That page reads from Task_Buffer, not from Submission_Log.
Testing doctrine

How to test without breaking the system

  • Use a test submission first.
  • Route it to Task_Buffer.
  • Confirm a new row appears in Task_Buffer.
  • Confirm Submission_Log did not change.
  • Confirm the task row includes source_submission_id.
  • Confirm the source JSON was copied or referenced correctly.

Failure condition: if routing edits or deletes the original log row, the design is wrong.
