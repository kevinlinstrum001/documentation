Executive Summary

Today we turned the Meadows HK request system from a rough Google Form experiment into a working communication pipeline. A user can submit a request, the system captures the submission, converts it into structured JSON, sends a phone alert through a dedicated Gmail account, displays the record as a readable card on the Google Site, preserves the raw JSON, and allows an acknowledgement action that sends a test acknowledgement email and logs the action.

Current milestone: The system now supports a complete loop: Submit → Notify → View → Inspect JSON → Acknowledge → Log acknowledgement.

The most important design rule is that Submission_Log remains the historical record. Other sheets and actions are derived from it rather than replacing or overwriting it.

What We Changed in the Google Form

The form was cleaned up so that it is easier to use while still capturing useful operational information. Instead of trying to enumerate every possible situation ahead of time, the form now uses a smaller number of routes plus flexible “Other” options.

Design improvement

  • Reduced the number of top-level routes so the form is easier to complete.
  • Added “Other” categories to catch edge cases that do not fit the current list.
  • Preserved location information such as unit, room, and area.
  • Allowed unexpected requests, such as “Activity Room — check microwave,” to still be captured coherently.
Key lesson: Categories do not need to be perfect yet. The system works if it reliably captures location, description, and the original submission.

JSON and the Permanent Log

The Google Form response sheet can remain messy because it is only the intake pipe. The useful record begins after Apps Script reads the submitted row, ignores blank branch fields, and creates a normalized JSON record.

LayerPurpose
Form ResponsesRaw intake from Google Forms. It can have many branch-generated columns.
Submission_LogPermanent receipt/history log. It should remain append-only and unchanged after write.
Normalized JSONFull structured record stored in a single cell in Submission_Log.
Acknowledgement_LogDerived action log showing which submissions have been acknowledged.

Important architecture rule

Submission_Log = what came in
Acknowledgement_Log = what was done in response
Future Task_Buffer = what needs action

Website Response Viewer

We deployed an Apps Script web app and embedded it into the Google Site on the Responses page. The viewer reads the JSON records from Submission_Log and displays each one as a card.

What the card viewer now does

  • Loads the newest submissions from Submission_Log.
  • Displays each submission as a readable card.
  • Shows summary, category, timestamp, submission ID, and answered fields.
  • Includes a collapsible Show raw JSON section.
  • Includes an Acknowledge button.
Why the raw JSON section matters: The card is the human-readable surface, while raw JSON is the exact structured record underneath.

Dedicated Notification Channel

We separated work notifications from the personal inbox by using the alternate Gmail account as the Meadows alert inbox. The Apps Script notification email now goes to the alternate account, and the phone is configured to notify for every message.

ChannelRole

Operational discovery: The email does not have to be the work surface. It only has to be the alert.

Acknowledge Button

We added a visible button to each response card, tested that it changed state in the browser, then connected it to Apps Script. The button now triggers a real server-side action.

Current acknowledgement behavior

  1. User clicks Acknowledge on a response card.
  2. The browser sends the submission_id to Apps Script.
  3. Apps Script looks up the original record in Submission_Log.
  4. Apps Script sends an acknowledgement email to the fixed test address.
  5. Apps Script appends a row to Acknowledgement_Log.
  6. The card button changes to Acknowledged.
Testing choice: Acknowledgements currently go to the alternate email account, not the supervisor. This lets the system be tested safely.

What We Proved Today

System functions proved

  • Google Form submission triggers Apps Script.
  • Apps Script creates normalized JSON.
  • Submission history is preserved.
  • Email notifications arrive on the phone.
  • The Google Site can display a live embedded viewer.
  • The viewer can read from the sheet and build cards.
  • Buttons on cards can call server-side Apps Script.
  • Acknowledgement actions can be logged separately.

Design principles proved

  • Keep raw intake separate from derived views.
  • Preserve immutable history.
  • Use JSON as the flexible record format.
  • Use cards for human readability.
  • Use email as notification, not the main workspace.
  • Build action buttons on top of source records.
  • Test with safe targets before contacting real users.

Design Pressures Learned from V1

These are the pressures that should guide the next version instead of guessing from imagination.

Observed pressureImplication for V2
Google Form branching creates messy columns.V2 should use fixed JSON objects from the beginning.
“Other” categories are necessary because many real cases are edge cases.V2 should preserve free-text issue descriptions and not over-force categories.
Cards are much easier to read than raw Sheets.V2 should use card views from the beginning.
Raw JSON is useful for confidence and debugging.Every important card should preserve a raw JSON view.
Dedicated Gmail alerts work well.V2 should keep a separate notification channel.
Acknowledge is immediately useful.V2 should support simple communication actions early.
Sorting/routing is still manual.Future buttons can route to Task Buffer, Meeting Notes, Suggestions, or Archive.
